01 Mission Context 任务背景

Lesson 09 你用管道把命令「串起来」了。但管道只管命令之间的 stdout。今天主管要你控制每一条流去哪里：

  • 📊 跑统计命令，正确结果要存进报告文件，错误要单独存进日志——不能混在一起。
  • 🔇 一个递归 find / grep 刷了满屏 Permission denied，要把它静音。
  • 📝 要写一个多行配置文件（不用一次次 echo）。
  • 🧯 最后：综合前 9 课，重建一个被删坏的研究目录。

核心是三条流：stdin(0)、stdout(1)、stderr(2)。重定向就是给它们「换个去向」。

Context → Need → Tool

要控制每条输出去哪里 → 需要重定向三流 → >/>>/</2>/2>&1/&>//dev/null/heredoc。

02 Knowledge 知识（≤25%，约 15–20 分钟）

3 concepts. Each: 英文定义 + 中文注释 + 心智模型 + 语法 + 实例 + 边界情况 + 工程场景 + 衔接点。

Concept 1 · Three streams + > / >> / <

English: Every process has three streams: stdin (0), stdout (1), stderr (2). > redirects stdout to a file (overwrite), >> appends, < feeds a file into stdin.

中文：每个进程有三条流：stdin(0) 输入、stdout(1) 标准输出、stderr(2) 错误。 > 把 stdout 覆盖写进文件、>> 追加、< 把文件喂给 stdin。

Syntax：

ls -l > files.txt             # stdout 覆盖写进 files.txt
ls -l >> files.txt            # stdout 追加到 files.txt
wc -l < reads.fastq           # 把文件喂给 wc 的 stdin（等价 wc -l reads.fastq）
sort < genes.txt              # 从文件读，排序

实例：grep "^@" reads.fastq > headers.txt——把 grep 的结果（stdout）存进 headers.txt，屏幕上不再显示。

边界情况 / 常见失败
  • > 会静默覆盖：文件已存在时 > 直接清空重写，不提示。重要文件先备份，或用 >>。
  • > 只重定向 stdout：报错（stderr）仍然打到屏幕，不会进文件。
  • < 大多数时候不必要：很多命令自己能读文件（wc -l file 不用 <）。但注意：wc -l < file 输出只有数字、不带文件名，而 wc -l file 带文件名。
  • < 和 > 方向别搞反：< 是「喂进命令」，> 是「从命令输出」。
工程场景 / 为什么需要它

「把结果存成报告」「把命令输出留档」是每天的动作。学会 >/>>，你的命令输出就能从屏幕「落地」成文件。

衔接点

Lesson 09 只提了 >/>> 一笔。这里吃透 stdin/stdout/stderr 三流。概念 2 讲最容易错的 stderr 重定向。

Concept 2 · stderr: 2> / 2>&1 / &>

English: stderr is file descriptor 2. 2> redirects stderr alone; 2>&1 merges stderr into wherever stdout currently points; &> redirects both at once (bash).

中文：stderr 是文件描述符 2。2> 单独重定向 stderr；2>&1 把 stderr 合并到 stdout 当前指向的地方；&> 一次重定向两者（bash 专属）。

Syntax：

grep -r "x" . 2> errors.log          # stderr 单独进文件，stdout 仍上屏
grep -r "x" . 2>/dev/null            # 静音 stderr
cmd > out.log 2>&1                    # stdout+stderr 都进 out.log（正确顺序）
cmd &> out.log                        # 同上，bash 简写
cmd > out.log 2> err.log              # 正确进 out，错误进 err（分开存）

实例：跑一条会刷屏的命令 find / -name "*.bam" 有大量 Permission denied：find / -name "*.bam" 2>/dev/null 把错误全丢进黑洞，屏幕只留真正的结果。

边界情况 / 常见失败
  • 2>&1 顺序极其重要：> file 2>&1 正确；2>&1 > file 错误（stderr 会留在终端）。记：先定 stdout 去向，再把 stderr 追过去。
  • &> 是 bash 专属：POSIX sh（/bin/sh）不认，脚本要可移植就别用，写 > file 2>&1。
  • 只 > 不 2> 时 stderr 照常上屏：这是最常见的「我以为都进文件了」错觉。
工程场景 / 为什么需要它

跑 pipeline 时「成功输出」和「错误日志」分开存，是排查问题的基本功。静音 Permission denied 更是扫目录时的日常。

衔接点

Lesson 09 的 Debug 3（stderr 不走管道）正是这里的引子。概念 3 讲黑洞 /dev/null 和多行输入 heredoc。

Concept 3 · /dev/null black hole + heredoc << / here-string <<<

English: /dev/null is a black hole that discards anything written to it. A heredoc <<EOF … EOF feeds multiple lines into stdin; a here-string <<< feeds a single string.

中文：/dev/null 是丢弃一切输出的黑洞。heredoc <<EOF…EOF 把多行文字喂给 stdin；here-string <<< 喂一个字符串。

Syntax：

cmd > /dev/null 2>&1              # 完全静音（stdout+stderr 都丢黑洞）
cat << EOF > config.txt          # heredoc 写多行到文件
name=user
cpu=8
EOF                                # 结束标记顶格，不能有空格

grep "TP53" <<< "TP53 BRCA1 EGFR"  # here-string 喂一个字符串
cat <<- EOF > x.txt               # <<- 允许用 Tab 缩进
cat << 'EOF' > x.txt              # 带引号的 EOF 禁止变量展开

实例：写一个脚本配置文件，不用 10 次 echo：cat << EOF > config.txt 后直接粘贴多行，最后顶格输入 EOF 结束，内容全写进文件。

边界情况 / 常见失败
  • heredoc 结束标记必须顶格：EOF 前有任何空格/Tab 都会导致 heredoc 不结束（除非用 <<-）。
  • /dev/null 是特殊设备文件：不是普通文件，写进去的东西永久消失，别指望能找回来。
  • here-string <<< 是 bash 专属：POSIX sh 不认。
  • 带引号的 EOF（<< 'EOF'）禁止变量展开：内容里的 $HOME 等不会被替换成值。
工程场景 / 为什么需要它

写脚本、写配置、静音噪音，这三件事每天都在发生。heredoc 让你把「多行内容」直接喂给命令，/dev/null 让你把「不想要的输出」一键清空。

Follow along. 不需要 sudo，建议在 tmux 里做。

name=user
cpu=8
mem=16G
EOF

05 Debug Challenge 排错挑战

5 个真实 Ubuntu Server 24.04 会遇到的报错。Problem → Think → Answer → Explanation。

调试 1 · grep -r "x" . > results.txt 后屏幕还冒 Permission denied
Problem：结果进文件了，但报错还在屏幕。
💭 Think：> 管的是哪条流？
Answer：> 只重定向 stdout，Permission denied 是 stderr。加 2>/dev/null 静音，或 2> err.log 单独存。
🧠 Explanation：stdout 和 stderr 是两条独立流，> 默认只碰 stdout。
调试 2 · cmd 2>&1 > log.txt 后 log.txt 里没有错误信息
Problem：顺序写反了，错误没进文件。
💭 Think：2>&1 和 > 谁先谁后？
Answer：2>&1 在 > 之前，stderr 先被指向终端 stdout，之后 > 只改了 stdout。改成 cmd > log.txt 2>&1。
🧠 Explanation：重定向按从左到右顺序执行。先定 stdout 去向，再让 stderr 追过去。
调试 3 · cat << EOF 输入完 EOF 也不结束
Problem：heredoc 不结束，一直等你输入。
💭 Think：结束标记 EOF 前面是不是有空格？
Answer：EOF 必须顶格（行首无任何空格/Tab）。或用 <<- 允许 Tab 缩进。
🧠 Explanation：结束标记必须单独成行且顶格，否则被当成内容的一部分。
调试 4 · echo "新报告" > report.txt 把昨天的报告覆盖没了
Problem：旧报告被静默清空重写。
💭 Think：> 是覆盖还是追加？
Answer：> 覆盖、>> 追加。要保留旧内容用 >>，或先 cp report.txt report.txt.bak。
🧠 Explanation：> 在文件已存在时直接截断，无提示。重定向前先想清楚。
调试 5 · wc -l < reads.fastq 输出只有 8，而 wc -l reads.fastq 输出 8 reads.fastq
Problem：同样的 wc，一个带文件名一个不带。
💭 Think：< 让命令知道了什么？
Answer：< 把内容喂给 stdin，wc 不知道文件名，所以只打印数字。直接给文件名则 wc 会带上名字。
🧠 Explanation：命令对「文件名参数」和「stdin」的行为不同。脚本里想只要数字时，< 反而更方便。

06 Engineering Scenarios 工程场景

先写自己的方案，再展开看答案。每个场景想「三个月后的人能否看懂」。

场景 1：跑一条统计 pipeline，正确结果要存成报告、错误要单独存日志（别混一起），方便同事分别查看。

参考方案

cmd > report.txt 2> errors.log——stdout 进报告、stderr 进日志，两条流各走各路。

场景 2：递归扫目录找 .bam，Permission denied 刷屏，你只要干净的结果清单。

参考方案

find /data -name "*.bam" 2>/dev/null——把 stderr 全丢黑洞，屏幕只剩真正的 .bam 路径。

场景 3：要写一个多行配置（用户名、CPU 数、内存、路径），不想用十几次 echo。

参考方案

heredoc：cat << EOF > pipeline.conf 后粘贴多行，顶格 EOF 结束，一次写完整份配置。

场景 4：一条命令很吵但结果不要，只要看它「成功还是失败」（退出码）。怎么彻底静音？

参考方案

cmd > /dev/null 2>&1 完全静音，然后 echo $? 看退出码判断成败（0=成功，非 0=失败）。
